## 1. Project Overview

The **Course Prerequisite Planner** is an interactive, console-based academic advisement and planning system built entirely around **Tree Data Structures**. 

In university curricula, students often face critical academic questions:
- *"What foundation courses must I complete before taking Advanced Machine Learning or Distributed Systems?"*
- *"What is the minimum number of sequential semesters required to reach my target course?"*
- *"Given the courses I have passed so far, which courses am I eligible to register for right now?"*
- *"How are credits distributed across semesters, academic years, and the entire degree?"*

While course dependencies are mathematically represented as Directed Acyclic Graphs (DAGs) at the curriculum level, this project demonstrates how **N-ary Trees** and **Hierarchical Multi-way Trees** can be used to solve academic planning problems through fundamental tree concepts:
1. **Recursive Tree Construction**
2. **Pre-order Traversal** with visual box-drawing branch rendering
3. **Tree Height / Maximum Depth** for critical-path semester scheduling
4. **Post-order Subtree Size** for prerequisite counting
5. **Leaf-Node Identification** for discovering foundational entry points
6. **Root-to-Leaf Path Printing via DFS with Backtracking** for exhaustive learning trajectories
7. **Post-order Traversal Sum** for bottom-up credit rollups
8. **Breadth-First Search (BFS) / Level-Order Traversal** for semester roadmaps
9. **Parent Pointer Navigation & Lowest Common Ancestor (LCA)** for academic relationship analysis
10. **LIFO Stack Command Reversal** for multi-level Undo support
11. **Recursion Call-Stack Visiting Sets** for cycle and integrity validation

> [!NOTE]
> **Planning Guidance Only:** Results and semester schedules generated by this planner are intended strictly for planning guidance. Official graduation criteria, course offerings, corequisites, and credit waivers remain subject to the institution's academic regulations.

## 2. The Two Trees

The architecture separates prerequisite analysis from degree organization using two complementary tree models:

```
                  ========================================
                         A. PREREQUISITE TREE
                  ========================================
                          [Root: Target Course]
                                   |
                +------------------+------------------+
                |                                     |
         [Prerequisite 1]                      [Prerequisite 2]
                |                                     |
       +--------+--------+                            |
       |                 |                            |
  [Foundation A]   [Foundation B]               [Foundation B]
   (Leaf Node)      (Leaf Node)                  (Leaf Node)

   * True N-ary Tree: Shared prerequisites (e.g. Foundation B)
     appear independently under each parent branch.

                  ========================================
                         B. CURRICULUM TREE
                  ========================================
                     [Root: Degree (B.Tech CSE)]
                                   |
                +------------------+------------------+
                |                                     |
            [Year 1]                              [Year 2] ...
                |                                     |
         +------+------+                       +------+------+
         |             |                       |             |
    [Semester 1]  [Semester 2]            [Semester 3]  [Semester 4]
         |
    +----+----+
    |         |
[Course A] [Course B] (Leaf Nodes with Credits)
```

### A. Prerequisite Tree
- **Node Structure:**
  ```cpp
  struct PreNode {
      std::string code;
      std::vector<PreNode*> prereqs;
  };
  ```
- **Root:** The student's chosen target course (e.g., `Deep Learning`).
- **Children:** Immediate prerequisite courses, expanded recursively down to foundation courses (leaf nodes).
- **Tree Guarantee:** If a prerequisite course is shared by multiple branches (e.g., `Basic Maths` required by both `Discrete Maths` and `Probability`), it appears under each branch independently. This preserves a **true tree structure** where every node has exactly one parent in the tree.

### B. Curriculum Tree
- **Node Structure:**
  ```cpp
  struct CurNode {
      std::string name;
      int credits = 0;
      std::vector<CurNode*> children;
      CurNode* parent = nullptr;
  };
  ```
- **Hierarchy:** `Degree -> Academic Year -> Semester -> Course`.
- **Parent Pointers:** Allow upwards bottom-up traversal from any course node to find its Semester, Year, and Degree, and compute the Lowest Common Ancestor (LCA) between any two courses in $O(h)$ time.

## 5. Complexity Table

| # | Feature Name | Tree Concept Applied | Time Complexity | Space Complexity | Description & Traversal Strategy |
|---|--------------|----------------------|-----------------|------------------|----------------------------------|
| 1 | Build Prerequisite Tree | Recursive Tree Construction | $O(n)$ | $O(h)$ call stack | Recursively instantiates `PreNode` subtrees for each prerequisite; visiting set prevents cycles. |
| 2 | Visual Branch Display | Pre-order Traversal | $O(n)$ | $O(h)$ stack | Visits root then children, printing branch box lines (`+-- `, `\|-- `, `\|   `). |
| 3 | Minimum Semesters Needed | Tree Height / Maximum Depth | $O(n)$ | $O(h)$ stack | Calculates `height = 1 + max(child heights)` to determine the longest prerequisite sequence. |
| 4 | Count Total Prerequisites | Subtree Size (Post-order) | $O(n)$ | $O(h)$ stack | Counts total tree instances ($1 + \sum \text{children}$) and unique courses via a set. |
| 5 | List Foundation Courses | Leaf-Node Identification | $O(n)$ | $O(h)$ stack | Identifies all nodes where `node->prereqs.empty()` (zero prerequisites). |
| 6 | All Learning Paths | DFS with Backtracking | $O(n \cdot h)$ | $O(h)$ path vector | Pushes nodes onto path vector; on reaching leaves, prints reversed root-to-leaf paths. |
| 7 | "What Can I Take Now?" | Prerequisite Completeness Check | $O(C \cdot k)$ | $O(C)$ | Evaluates whether all prerequisites of a course are contained in the completed set. |
| 8 | Curriculum Credits View | Post-order Traversal Sum | $O(N)$ | $O(H)$ stack | Bottom-up rollup: course credits $\rightarrow$ semester totals $\rightarrow$ year totals $\rightarrow$ degree total. |
| 9 | Search Course (DFS/BFS) | Tree Search + Parent Pointers | $O(N)$ | $O(N)$ queue / $O(H)$ stack | Searches curriculum tree; backtracks via parent pointers to show full ancestral path. |
| 10 | Semester-Wise Plan | Level-Order Traversal (BFS) | $O(N)$ | $O(W)$ queue | Uses a queue to traverse Degree $\rightarrow$ Years $\rightarrow$ Semesters $\rightarrow$ Courses level-by-level. |
| 11 | Add/Remove Course/Prereq | Tree Node Insertion / Subtree Deletion | $O(h)$ / $O(\text{subtree})$ | $O(1)$ | Inserts or detaches nodes from parent; recursively deallocates memory; recalculates credits. |
| 12 | Lowest Common Ancestor | LCA via Parent Pointers | $O(h)$ | $O(h)$ path vectors | Reconstructs root-to-node paths via parent pointers; compares paths to find the divergence point. |
| 13 | Multi-Level Undo | LIFO Stack (Command Pattern) | $O(1)$ stack op | $O(U)$ undo stack | Reverts addition/deletion of courses or prerequisites by popping the inverse command. |
| 14 | Data Validator | Cycle Detection via Call Stack | $O(C + E)$ | $O(C)$ set | Detects self-loops, missing course codes, circular chains, and file discrepancies. |

*(Note: $n$ = nodes in prerequisite tree, $h$ = height of prerequisite tree, $N$ = total nodes in curriculum tree $\approx 45$, $H$ = height of curriculum tree $= 4$, $C$ = unique courses $= 31$, $k$ = max prerequisites per course).*

## 7. Viva Q&A (Top 10 Questions and Answers)

### Q1: Why did you choose a tree data structure instead of a graph for this project?
> **Answer:**  
> A tree provides a clear hierarchical view where a chosen course acts as the root and its dependencies unfold downward in branching levels. This structure makes several key calculations straightforward and elegant: tree height immediately yields the minimum sequential semesters needed; subtree size calculates total prerequisite dependencies; leaf nodes pinpoint entry-level foundation courses; and pre-order traversal produces intuitive, indented branch visualizations.

---

### Q2: Which tree traversals are used in this project, where are they applied, and why?
> **Answer:**  
> 1. **Pre-order Traversal (Root $\rightarrow$ Children):** Used for printing the prerequisite tree and hierarchical curriculum with box branches, because a parent must be printed before its nested children.
> 2. **Post-order Traversal (Children $\rightarrow$ Root):** Used for:
>    - Calculating subtree size (counting prerequisite instances).
>    - Aggregating credit totals in the Curriculum Tree (summing Course credits $\rightarrow$ Semester totals $\rightarrow$ Year totals $\rightarrow$ Degree total).
>    - Recursive memory deallocation (`destroyPreTree`, `destroyCurTree`) so child nodes are safely deleted before deleting the parent.
> 3. **Level-Order Traversal (BFS using a Queue):** Used for the semester-wise academic plan, processing Degree (Level 0), Years (Level 1), Semesters (Level 2), and Courses (Level 3) tier-by-tier.
> 4. **DFS with Backtracking:** Used for finding all distinct learning trajectories from foundation leaves up to the target root.

---

### Q3: What is the time complexity of course insertion and deletion in the Curriculum Tree?
> **Answer:**  
> - **Insertion:** $O(h)$ where $h$ is the curriculum tree height ($h \le 4$). Locating the target semester takes constant bounded steps, and inserting the child node is $O(1)$. Recomputing credits is $O(N)$ where $N \approx 45$.
> - **Deletion:** $O(h)$ to locate the course under its semester node, $O(1)$ to detach the pointer and deallocate the node, and $O(N)$ to update parent credit sums. In asymptotic terms relative to tree height, both are $O(h)$.

---

### Q4: Why is a shared prerequisite repeated in the prerequisite tree?
> **Answer:**  
> In a formal tree data structure, every node except the root must have **exactly one parent**. If course $A$ and course $B$ both require `Basic Maths`, pointing both $A$ and $B$ to a single shared `Basic Maths` node would introduce multi-parenting and create a Directed Acyclic Graph (DAG) rather than a tree. By creating independent node instances of `Basic Maths` in each branch, we preserve strict tree properties, ensuring tree algorithms (such as tree height, independent subtree deletions, and path printing) work cleanly without infinite loops or shared-ownership complications.

---

### Q5: What is the fundamental limitation of a tree representation compared to a DAG for prerequisites?
> **Answer:**  
> In reality, course prerequisites form a **Directed Acyclic Graph (DAG)**. The main limitation of our tree representation is **node duplication**: when multiple intermediate courses share the same prerequisite, that prerequisite is cloned into multiple subtrees. In pathological dependency chains, this can lead to exponential tree expansion ($O(b^d)$ nodes for branching factor $b$ and depth $d$). A DAG representation with topological sorting avoids duplication by having shared nodes, but requires graph algorithms like Kahn's algorithm or Tarjan's SCC algorithm.

---

### Q6: How does the program calculate the minimum semesters needed using tree height?
> **Answer:**  
> Because each prerequisite in a chain must be completed before the subsequent course can begin, the minimum number of sequential academic terms required corresponds directly to the **longest path from the root (target course) to any foundation leaf node**. Mathematically, this is the height of the prerequisite tree:
> $$\text{Height}(\text{node}) = 1 + \max_{\text{child} \in \text{prereqs}}(\text{Height}(\text{child}))$$
> A course with zero prerequisites has a height of 1 (taken in 1 semester).

---

### Q7: How does post-order traversal sum up credits at the semester, year, and degree levels?
> **Answer:**  
> Post-order traversal guarantees that all children of a node are evaluated before the node itself is processed. Leaves (courses) have predefined credit values. When the post-order recursion returns from the leaves to a Semester node, it sums their credits. When it returns to a Year node, it sums the semester totals. Finally, at the Degree root, it sums all academic year credits.

---

### Q8: How is the Lowest Common Ancestor (LCA) implemented, and what is its academic meaning?
> **Answer:**  
> Each curriculum node maintains a `parent` pointer. To find the LCA of Course 1 and Course 2:
> 1. We trace parent pointers from Course 1 up to the Degree root, storing the path in vector $A$.
> 2. We trace parent pointers from Course 2 up to the Degree root, storing the path in vector $B$.
> 3. We compare vectors $A$ and $B$ from root downwards; the last matching node before they diverge is the LCA.
> 
> **Academic Meaning:**
> - If LCA is a **Semester** node: The two courses are taken concurrently in the **same semester**.
> - If LCA is a **Year** node: Both courses are taken in the **same academic year**, but in different semesters.
> - If LCA is the **Degree** root: The two courses belong to **different academic years**.

---

### Q9: How does cycle detection work during recursive tree construction without graph algorithms?
> **Answer:**  
> During recursive construction (`buildPrereqTree`), we maintain an `unordered_set<string> visitingSet` representing the current recursion call stack. Before recursing into a prerequisite child, we check if that course is already in `visitingSet`. If present, an ancestor in the current active path is requiring itself, proving a circular prerequisite dependency. The recursion immediately flags an error and stops expanding that branch. When recursion unwinds, the course is erased from `visitingSet`, ensuring only ancestor nodes in the active branch are tracked.

---

### Q10: How does the Undo feature work using a Stack?
> **Answer:**  
> We use the **Command Pattern** backed by an `std::stack<UndoAction>`. Whenever a user modifies the catalog (e.g., `ADD_COURSE`, `REMOVE_COURSE`, `ADD_PREREQUISITE`, `REMOVE_PREREQUISITE`), the operation details and previous state are pushed onto the stack. Selecting "Undo last change" pops the top action from the stack and executes its inverse:
> - Undoing `ADD_COURSE` deletes the course node and cleans up memory.
> - Undoing `REMOVE_COURSE` re-inserts the node, re-links its parent, restores its prerequisites, and restores referencing courses.
> - Stack operations operate in $O(1)$ time.

## 8. Memory Management and Safety

- **Zero Memory Leaks:** Every `new PreNode` and `new CurNode` allocation is paired with dedicated recursive post-order destructor functions:
  ```cpp
  void destroyPreTree(PreNode* root);
  void destroyCurTree(CurNode* root);
  ```
- All dynamically generated prerequisite trees are destroyed immediately after their analysis or display completes.
- The Curriculum Tree is deallocated cleanly in `CoursePlanner::~CoursePlanner()` upon program exit.
- All user inputs are validated against non-numeric data, missing inputs, and invalid ranges without crashing.
